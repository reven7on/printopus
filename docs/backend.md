# Backend Printopus

Первый backend-этап реализован через Next.js Route Handlers, Prisma и PostgreSQL.

## Доступные маршруты

### `GET /api/catalog`

Возвращает активные товары, цвета, размеры, методы печати, форматы и скидки. Денежные значения передаются числами в BYN.

### `POST /api/orders`

Создаёт заказ и одну позицию заказа. Клиент передаёт только выбранные параметры и контактные данные:

```json
{
  "submissionId": "0f4b6918-0f27-4c91-80b7-f1b4e9256050",
  "customerName": "Анна",
  "customerPhone": "+375 (29) 555-20-30",
  "contactMethod": "phone",
  "fulfillmentMethod": "pickup",
  "deliveryAddress": null,
  "comment": "Позвонить после 18:00",
  "productSlug": "shirt",
  "color": "white",
  "size": "M",
  "sizeDistribution": [
    { "size": "S", "quantity": 5 },
    { "size": "M", "quantity": 10 },
    { "size": "L", "quantity": 5 }
  ],
  "printMethodSlug": "dtf",
  "printFormatCode": "A4",
  "placement": "center",
  "quantity": 20,
  "design": { "front": [] }
}
```

Цена из браузера намеренно не принимается. Сервер заново получает цены и скидку из PostgreSQL, проверяет доступность выбранных параметров и сохраняет рассчитанные значения в заказе.

`sizeDistribution` необязателен: поле `size` сохраняется для совместимости. Если распределение передано, размеры должны быть уникальны и доступны для товара, количества — положительными целыми числами, а их сумма должна совпадать с `quantity`.

`submissionId` генерируется браузером один раз для попытки оформления. Повторный запрос с тем же UUID возвращает уже созданный заказ с HTTP 200 и `duplicate: true`, поэтому потерянный HTTP-ответ не создаёт второй заказ.

Конфигуратор отправляет `multipart/form-data`: JSON заказа находится в поле `order`, исходные изображения — в повторяемом поле `files`, а точные PNG-ракурсы конструктора — в `previews`. JSON-вариант без файлов сохранён для интеграций. Сервер принимает только JPEG, PNG и WebP, проверяет сигнатуру и полное декодирование, ограничивает размер и разрешение, затем перекодирует изображение без исходных метаданных. Файлы и превью сохраняются на постоянный диск VPS вне `public`, а в PostgreSQL находятся метаданные и связи с заказом.

В той же транзакции, что и заказ, создаётся `telegram_deliveries`. Приложение пытается отправить уведомление сразу, а отдельный `telegram-worker` повторяет доставку после временных ошибок или перезапуска приложения. После 12 неудачных попыток запись получает статус `FAILED`; менеджер видит это в карточке и может поставить уведомление в очередь повторно.

### `GET /api/admin/assets/:id`

Возвращает файл макета как скачиваемое вложение только при действующей сессии администратора. Ответ запрещает MIME-sniffing и кеширование приватного файла.

### `GET /api/health`

Проверяет соединение с PostgreSQL и доступность каталога загрузок для чтения и записи. Используется Docker для контроля состояния приложения.

Ошибки имеют единый формат:

```json
{
  "error": {
    "code": "INVALID_ORDER",
    "message": "Укажите адрес доставки.",
    "field": "deliveryAddress"
  }
}
```
