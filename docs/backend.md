# Backend Printopus

Первый backend-этап реализован через Next.js Route Handlers, Prisma и PostgreSQL.

## Доступные маршруты

### `GET /api/catalog`

Возвращает активные товары, цвета, размеры, методы печати, форматы и скидки. Денежные значения передаются числами в BYN.

### `POST /api/orders`

Создаёт заказ и одну позицию заказа. Клиент передаёт только выбранные параметры и контактные данные:

```json
{
  "customerName": "Анна",
  "customerPhone": "+375 (29) 555-20-30",
  "contactMethod": "phone",
  "fulfillmentMethod": "pickup",
  "deliveryAddress": null,
  "comment": "Позвонить после 18:00",
  "productSlug": "shirt",
  "color": "white",
  "size": "M",
  "printMethodSlug": "dtf",
  "printFormatCode": "A4",
  "placement": "center",
  "quantity": 20,
  "design": { "front": [] }
}
```

Цена из браузера намеренно не принимается. Сервер заново получает цены и скидку из PostgreSQL, проверяет доступность выбранных параметров и сохраняет рассчитанные значения в заказе.

Конфигуратор отправляет `multipart/form-data`: JSON заказа находится в поле `order`, а исходные изображения — в повторяемом поле `files`. JSON-вариант без файлов сохранён для интеграций. Сервер принимает только JPEG, PNG и WebP, проверяет сигнатуру и полное декодирование, ограничивает размер и разрешение, затем перекодирует изображение без исходных метаданных. Файлы сохраняются на постоянный диск VPS вне `public`, а в PostgreSQL находятся только метаданные и связь с позицией заказа.

### `GET /api/admin/assets/:id`

Возвращает файл макета как скачиваемое вложение только при действующей сессии администратора. Ответ запрещает MIME-sniffing и кеширование приватного файла.

### `GET /api/health`

Проверяет соединение с PostgreSQL и доступность каталога загрузок для чтения и записи. Используется Docker для контроля состояния приложения.

Ошибки имеют единый формат:

```json
{
  "error": {
    "code": "INVALID_ORDER",
    "message": "Укажите адрес доставки.",
    "field": "deliveryAddress"
  }
}
```
