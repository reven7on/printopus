# Тестовый деплой на Render

Render запускает этот проект как один Web Service и отдельную управляемую
PostgreSQL. В одном контейнере работают Next.js и Telegram delivery worker,
поэтому оба процесса используют один каталог загруженных макетов. Миграции,
начальное заполнение каталога и настройка Telegram webhook выполняются при
старте контейнера.

Конфигурация предназначена для тестового окружения. Бесплатный Web Service
засыпает после периода без входящих запросов, его файловая система временная,
а бесплатная PostgreSQL действует ограниченное время. Не используйте этот
Blueprint как production без апгрейда базы и подключения постоянного диска.

## 1. Отправка ветки в GitHub

Render должен получить доступ к Git-репозиторию. Создайте приватный репозиторий
на GitHub, затем из корня проекта выполните:

```sh
git remote add origin git@github.com:YOUR_ACCOUNT/printopus.git
git push -u origin codex/render-deploy
```

Если `origin` уже существует, первую команду выполнять не нужно.

## 2. Создание Blueprint

1. В Render откройте **New → Blueprint**.
2. Подключите GitHub и выберите репозиторий проекта.
3. Выберите ветку `codex/render-deploy`.
4. Оставьте путь Blueprint равным `render.yaml`.
5. Укажите секретные переменные, которые запросит Render.

Обязательные значения:

- `ADMIN_USERNAME` — имя администратора;
- `ADMIN_PASSWORD` — отдельный сложный пароль тестовой админки;
- `TELEGRAM_BOT_TOKEN` — токен отдельного тестового бота;
- `TELEGRAM_ADMIN_CHAT_ID` — ID личного чата или группы менеджеров;
- `TELEGRAM_WEBHOOK_SECRET` — строка из 16–256 латинских букв, цифр,
  подчёркиваний или дефисов.

Безопасный webhook secret можно создать локально:

```sh
openssl rand -hex 32
```

`ADMIN_SESSION_SECRET` создаёт Render. `DATABASE_URL` и `SITE_URL` Blueprint
получает автоматически. Не загружайте локальный `.env` целиком и не используйте
production Telegram-бота для тестового окружения.

Для Telegram-группы после создания сервиса добавьте в его Environment значение
`TELEGRAM_MANAGER_USER_IDS`: числовые Telegram ID менеджеров через запятую.
Для личного чата переменную можно оставить пустой.

## 3. Проверка первого запуска

Первый запуск дольше обычного: Render собирает образ, применяет Prisma-миграции,
создаёт каталог и регистрирует webhook. Деплой считается готовым только после
успешного healthcheck `GET /api/health`.

Проверьте адреса, выданные Render:

- `/` — главная;
- `/configurator` — конструктор;
- `/admin` — админка;
- `/api/health` — ответ `{"status":"ok"}`.

После этого создайте тестовый заказ, проверьте уведомление в Telegram и смену
статуса кнопкой в сообщении.

## 4. Ограничения бесплатного варианта

- Загруженные пользователями макеты пропадут после остановки, перезапуска или
  нового деплоя сервиса. Записи заказов сохранятся в PostgreSQL, но связанные
  файлы станут недоступны.
- После простоя первый запрос ждёт холодный запуск. В это время выполняются
  миграции, проверка каталога и настройка webhook.
- Бесплатная PostgreSQL предназначена только для временной демонстрации.
- `UPLOAD_MIN_FREE_BYTES=0` разрешён только для такого тестового окружения.

## 5. Перевод Render-окружения на постоянное хранение

Перед использованием реальных заказов:

1. Переведите Web Service и PostgreSQL на платные планы.
2. В Web Service откройте **Disks → Add Disk**.
3. Смонтируйте диск в `/var/lib/printopus/uploads`.
4. Измените `UPLOAD_MIN_FREE_BYTES` как минимум на `268435456`.
5. Используйте production-домен и отдельного production Telegram-бота.
6. После добавления своего домена замените `SITE_URL` на его HTTPS-адрес и
   выполните redeploy, чтобы Telegram webhook указывал на новый домен.

Диск нельзя разделить между несколькими Render-сервисами. Поэтому приложение и
Telegram delivery worker намеренно остаются в одном Web Service. Для будущего
горизонтального масштабирования сначала перенесите загрузки в S3-совместимое
объектное хранилище.
